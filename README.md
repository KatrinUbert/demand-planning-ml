# Demand Planning ML

Прогноз недельного спроса и расчёт запаса для интернет-магазина. Python, pandas, NumPy, LightGBM, scikit-learn, FastAPI, Docker. Опциональный LLM-слой объясняет готовый прогноз через API совместимого провайдера.

## Задача

Заказ по последним продажам запаздывает при изменении спроса. Слишком большой запас увеличивает стоимость хранения, слишком маленький приводит к потерянным продажам. Проект сравнивает прогноз LightGBM с простым baseline и показывает, как разные прогнозы меняют запас в симуляторе.

Это самостоятельная публичная реализация на синтетических данных. Здесь нет данных, кода или измерений компании. Результаты симуляции описывают только заданный сценарий.

## Что реализовано

- 24 товара и 160 недель истории с сезонностью, трендом и автокоррелированным шумом; seed 42.
- Прогноз на одну неделю вперёд: отдельные LightGBM-модели для квантилей 0.50 и 0.85. Отрицательные прогнозы обрезаются до нуля, q85 ограничивается снизу q50; метрики считаются после этой обработки.
- Лаги 1, 2, 4, 52 недели, скользящие средние и стандартное отклонение. Все агрегаты сдвинуты на неделю; календарь целевой недели известен заранее.
- Общие для всех товаров временные границы train, validation и test. Модели обучаются только на train, параметры заданы заранее. Validation и test не используются для подбора параметров.
- Baseline: среднее за последние четыре недели с квантильными поправками остатков, рассчитанными только на train.
- MAE, WAPE, pinball loss для обоих квантилей, фактическое покрытие q85 по каждому периоду; ошибки на test по товарам и важность признаков по gain.
- Симуляция пополнения запасов, REST API, manifest с версиями библиотек и SHA-256 набора данных.

Оценка выполняется как последовательный прогноз на неделю вперёд: к каждой следующей неделе доступны фактические продажи предыдущей. Это не прогноз сразу на весь тестовый период из одной исходной даты. Артефакт модели намеренно остаётся обученным на train, чтобы API и отчёт использовали одну версию.

## Запуск

Нужен Python 3.12 или 3.13. Из директории проекта:

```bash
python -m venv .venv
```

Активация в Windows PowerShell:

```powershell
.\.venv\Scripts\Activate.ps1
```

Активация в Linux/macOS:

```bash
source .venv/bin/activate
```

```bash
pip install -r requirements.txt
python -m demand_planning.train --output artifacts
python -m demand_planning.demo --artifacts artifacts
uvicorn demand_planning.api:app --host 127.0.0.1 --port 8000
```

Документация API: `http://127.0.0.1:8000/docs`.

В другом терминале:

```bash
curl -X POST http://127.0.0.1:8000/forecast -H "Content-Type: application/json" --data-binary @artifacts/request.json
```

В Windows вместо `curl` можно вызвать `curl.exe`. Для каждого товара API принимает минимум 52 последовательные недели, начинающиеся в понедельник. Дубли, пропуски, отрицательные значения и неизвестные SKU отклоняются. Для нового товара модель нужно переобучить с его историей. `MODEL_PATH` позволяет указать иной локальный артефакт.

После обучения появляются:

```text
artifacts/
  model.joblib
  manifest.json
  metrics.json
  synthetic_history.csv
  predictions.csv
  feature_importance.csv
  request.json
```

Артефакты и данные исключены из Git. `joblib` следует загружать только из доверенного локального источника.

## LLM-объяснение

`POST /explain` принимает тот же запрос и необязательный `use_llm`. По умолчанию возвращается локальное текстовое объяснение без сети. При `use_llm: true` необходимы переменные окружения:

```text
LLM_API_BASE=https://your-provider.example/v1
LLM_API_KEY=...
LLM_MODEL=...
```

Этот режим отправляет провайдеру только идентификатор товара, неделю и готовые прогнозы. LLM не вычисляет спрос и не изменяет числовой результат. Ответ содержит исходные факты отдельным полем. Сгенерированный текст может ошибаться, поэтому числовые значения нужно брать из `facts`. В демо внешняя модель не вызывалась.

## Симуляция запасов

В начале целевой недели заказ доводит доступный запас до округлённого q85 с учётом остатка с прошлой недели. Прогноз использует историю по предыдущую неделю включительно. В симуляторе принято мгновенное пополнение до спроса целевой недели: lead time равен нулю, горизонт прогноза — одна неделя. Очередь поставок не моделируется. Поставщик всегда может выполнить заказ, ограничения бюджета, партий, сроков годности и общей ёмкости склада отсутствуют. Неудовлетворённый спрос теряется.

Цена хранения — 0.6 условной единицы за товар в конце недели, маржа продажи — 4.0. Отчёт содержит затраты на хранение, потерянную маржу, их сумму и долю удовлетворённого спроса. Значение 0.85 задано для демонстрации; при такой функции издержек оптимальный уровень сервиса нужно выбирать отдельно на validation.

Синтетический target — полностью наблюдаемый спрос при наличии товара. В реальной задаче продажи при дефиците цензурированы; восстановления такого спроса этот проект не реализует. Поэтому цифры нельзя переносить на работу реального склада.

## Результат демонстрационного запуска

Запуск 16 октября 2026 года: Python 3.12.14, pandas 2.3.3, NumPy 2.5.4, scikit-learn 1.9.1, LightGBM 4.7.0. Параметры генератора и seed — из быстрого запуска. Полный компактный отчёт с версиями и хешем данных: [reports/demo_metrics.json](reports/demo_metrics.json).

| Период | Число наблюдений | WAPE LightGBM | WAPE baseline |
| --- | ---: | ---: | ---: |
| Train: 02.01.2023–18.03.2024 | 1536 | 3.72% | 6.48% |
| Validation: 25.03.2024–19.08.2024 | 528 | 5.25% | 6.78% |
| Test: 26.08.2024–20.01.2025 | 528 | 5.55% | 6.90% |

На test MAE составила 4.6818 против 5.8125 у baseline; pinball loss q85 — 1.4933 против 1.8370. Покрытие q85 у модели — 80.68% вместо номинальных 85%: квантиль недокалиброван, поэтому его нельзя считать гарантией уровня сервиса. Подбор калибровки по test после этого запуска не выполнялся.

В симуляции на test расходы на хранение составили 1799.4 против 2225.4 условной единицы, сумма хранения и потерянной маржи — 3335.4 против 4121.4. Доля удовлетворённого спроса — 99.14% против 98.93%. Эти результаты получены при мгновенном пополнении, неограниченном поставщике и синтетическом спросе; они не являются экономическим эффектом в реальной компании.

## Docker

```bash
docker build -t demand-planning-ml .
docker run --rm -p 8000:8000 demand-planning-ml
```

Образ обучает демо-модель при сборке. Это удобный демонстрационный запуск; в рабочем процессе обучение и развертывание сервиса следует разделить.

## Ограничения и развитие

Однонедельный горизонт, только знакомые товары, небольшой синтетический набор. Промоакции, цены и сроки поставки не моделируются. Полезное продолжение — rolling-origin backtest, калибровка квантилей, несколько горизонтов, признаки промо и мониторинг качества по сегментам. Пока здесь нет автоматического переобучения и мониторинга в работающем сервисе.
